# 精简来源查询：性能改进的配对复测

2026-11-12。此前来源追溯准确率对照发现原始 DSH 能正确完成任务；完整插件视图额外返回正文及来源元数据，未必节省 token。本阶段检验 `evidence_trace` 是否能在相同来源追溯结果下减少上下文和调用开销。**这是看到第一阶段后开发的性能改进，不是独立验证集，也不是新增语义识别算法。**

## 改进

新增生产工具 `evidence_trace(case_id,evidence_ids,offset?,limit?)`：最多查询 20 条已存材料，沿同一份记录的 derivation 图追溯；返回案例来源家族数及分页的材料/源头对应项。每页最多 200 项，不重复正文和全图。保留未知独立性声明；原文仍由 evidence_get、evidence_context 或导出获取。只适用于来源记账问题，不能代替阅读正文后判断事实。

## 对照

沿用第一阶段六张固定图、192 条材料、24 条查询及三个顺序种子。原始完整材料、原插件完整视图、新精简查询三组；每组均在实际 DSH Native 和 PTC 下运行三次，共 18 Session。模型 deepseek-official/deepseek-flash、reasoning=low、每 completion 16384 token、8 次 completion/300 秒上限。全部按案例分页。

三组相同提示，明确提供所有格式的字段含义；PTC 可编写 JavaScript。原始组和完整插件组拥有全部输入关系及正文；精简组是生产 trace 函数对同一批请求的结果，没有人为注入金标准。此前完整原始输入的哈希必须保持一致。正确答案仍由独立图 oracle 和 Python 复核，不改变 lineage 的语义。

`origin_packet` 是受控实验的统一传输接口，不是新增产品工具；输入来自生产实现。另通过实际 DSH Native/PTC 执行生产 `evidence_trace` 验证接入。实验衡量调用选定工具后的成本，不声称测过自主选择工具、联网获取引用或真实子 Agent 汇报的全流程。

## 预定评分

- 每组 18 个案例判定、72 条来源集合查询；这是六个固定图的三次重复，不是 18 个独立现实样本。
- 正确率和源头误删/增加与第一阶段同标准。完整性失败与模型未完成单列，不制造准确率收益。
- 主 Agent input/cache/output/total token、completion 次数、模型工具调用、嵌套工具次数、耗时分别记录；背景标题请求不含在 token 总量中，不称为账单。
- 在 Native 内比较三组，在 PTC 内比较三组；不把 Native 原始组与 PTC 新工具混比后宣称纯插件收益。
- 如果新接口更便宜且答案保持一致，可声称“在此来源追溯任务中减少上下文/执行开销”；不能声称降低错误结论率、自动识别冲突或证明真实来源独立。
- 若 PTC 基线同样高效，或收益不稳定，完整报告，不排除不利运行。不修改数据直到出现有利结论。
